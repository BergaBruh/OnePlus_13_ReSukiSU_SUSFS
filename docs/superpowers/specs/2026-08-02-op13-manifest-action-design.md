# Проектирование матрицы сборок OP13 и сокращения манифестов

## Мотивация

Репозиторий должен собирать только поддерживаемые варианты OnePlus 13, а
отслеживаемые манифесты не должны сохранять неподдерживаемую матрицу устройств.
Избыточные задания по модели или региону повышают время CI и допускают случайную
сборку вне утверждённого набора.

## Архитектура и поток данных

Существующий workflow по прежнему запускается от текущего push-триггера. Его
матрица содержит только шесть конфигураций из таблицы выше; `fail-fast: false`.
Каждый элемент матрицы создаёт одно независимое build-задание, ZIP-артефакт и
артефакт метаданных релиза. Имена обоих артефактов включают уникальный slug
матрицы: это устраняет текущий риск коллизии matrix-output и коллизии имён
артефактов между параллельными заданиями.
Не создаются отдельные задания или декартовы подматрицы по модели, региону,
версии либо другим признакам.

Перед передачей входа в существующий build action задание последовательно:

1. Проверяет существование JSON-конфигурации.
2. Разбирает её как JSON.
3. Извлекает указанный в ней путь манифеста и проверяет существование файла.
4. Только после успешной проверки передаёт прежние входы в действие сборки.

Логика закреплённых состояний ReSukiSU/SUSFS и уже используемые входы сборки не
меняются: сокращение матрицы не должно ослабить pinning или подменить исходники.
Исключение необходимо для устранения коллизии upload-артефактов: composite
action получает необязательный вход `upload_final_zip` со значением по умолчанию
`true`, а его внутренний шаг загрузки ZIP выполняется только при `true`. Поэтому
все существующие callers сохраняют прежнюю загрузку ZIP без изменений. Только
OP13 matrix workflow передаёт `upload_final_zip: false` и самостоятельно
загружает ZIP с уникальным slug вместе с метаданными.

Для диагностических артефактов composite action также получает необязательный
`artifact_slug` с пустым значением по умолчанию. Пустое значение сохраняет
прежнее имя `debug_<model>_<os>.zip` без изменений. Непустое значение проверяется
по `^[A-Za-z0-9._-]+$` и добавляется к имени через подчёркивание; OP13 matrix
workflow передаёт уникальный `matrix.slug`.

Каждое успешное build-задание загружает ровно один ZIP с уникальным именем и
отдельный JSON-артефакт метаданных со slug, путями конфигурации и манифеста,
совместимостью, OOS, известными kernel/KMI, закреплёнными ревизиями ReSukiSU и
SUSFS, именем ZIP и его SHA-256. Совместимость указывается только по
подтверждённому соответствию: `CPH2649` — IN, `CPH2653` — EU/GLO, `CPH2655` —
NA/US, `PJZ110` — CN. Для базовых конфигураций без такого явного соответствия
в поле совместимости выводится имя конфигурации/манифеста; регион не
придумывается. Одинаковые по содержимому конфигурации не объявляются разными
региональными вариантами.
Для строки `oos16-op13-global-6-6-118` поле `kernel_kmi` берётся из
авторитетного `.target.kmi` закреплённого state JSON после проверки формата.
Остальные пять строк сохраняют fallback на kernel-version output build action;
новые KMI для них не предполагаются.

Единственное нематричное задание публикации зависит от всех шести build-заданий
и запускается только при их общем успехе. Оно скачивает все шесть пар
артефактов, проверяет точное число метаданных и ZIP, уникальность шести slug и
имён ZIP, соответствие каждого ZIP своей метаинформации и SHA-256. Затем оно
генерирует Markdown-таблицу релиза из метаданных со столбцами: slug
конфигурации, точные конфигурация и манифест, совместимость, OOS, kernel/KMI
(если известны), ReSukiSU, SUSFS, ZIP и SHA-256. Никакие фиксированные строки
вида Global/CPH2653 в описании релиза не используются.

Только после всех проверок publish-задание выполняет ровно один вызов
`gh release create`, создавая атомарный общий релиз с тегом
`op13-all-r${RUN_NUMBER}-a${RUN_ATTEMPT}` и заголовком
`OnePlus 13 ReSukiSU + SUSFS builds r${RUN_NUMBER}`. При ошибке любого build
задания, нехватке, дублировании или несовпадении артефактов публикация не
запускается: частичный релиз не создаётся.

## Дополнение: независимое управление module overlay

В JSON-конфигурацию добавляется булево поле `module_overlay`, независимое от
`custom_patches`. Отсутствующее поле означает `false`: шаг
`Parse op_config_json` явно записывает `OP_MODULE_OVERLAY=false` в
`GITHUB_ENV`. Если поле присутствует, валидация принимает только JSON-значения
`true` и `false`. Отдельный input composite action не добавляется.

Все шесть OP13-конфигураций получают явное значение
`"module_overlay": false`: `configs/oos15/OP13-6.6.30.json`,
`configs/oos15/OP13-CPH-6.6.56.json`, `configs/oos15/OP13-CPH.json`,
`configs/oos15/OP13-PJZ.json`, `configs/oos16/OP13-GLOBAL-6.6.118.json` и
`configs/oos16/OP13.json`.

Вся логика module overlay — применение
`0001-module-Add-module-intercept-and-overlay-mechanism.patch`, подготовка
`convert_overlay.sh`, выбор и копирование модулей и добавление скопированных
модулей в hash ccache — переносится из `Apply Other Patches` в отдельный шаг.
Единственное условие запуска нового шага:
`${{ env.OP_MODULE_OVERLAY == 'true' }}`; оно не зависит от
`OP_CUSTOM_PATCHES`. Внутренняя проверка версии ядра сохраняется: для ядер
`<= 5.16` overlay по-прежнему пропускается. Для включённого overlay на
подходящем ядре до изменения дерева проверяется наличие требуемого patch-файла
и payload модулей; отсутствие любого из них завершает шаг с actionable
сообщением, содержащим отсутствующий путь. Остальная логика
`custom_patches` — ptrace, hmbird и общие оптимизационные патчи — остаётся без
изменений.

Контрактные тесты фиксируют независимость `module_overlay` от
`custom_patches`, default `false` для отсутствующего поля, отклонение значений
кроме `true`/`false`, явный `false` во всех шести OP13-конфигурациях, понятную
ошибку при отсутствующем patch/modules payload и полное отсутствие overlay-
логики в `Apply Other Patches`. Приёмка требует успешного локального запуска
контрактного теста, затем успешного CI-прогона всех шести строк матрицы и ровно
одной общей публикации.

## Поведение при ошибках

Ошибка отсутствующего/некорректного JSON или отсутствующего манифеста завершает
только соответствующее matrix-задание до сборки и с понятным сообщением. Из-за
`fail-fast: false` остальные пять конфигураций продолжают выполняться. ZIP и
метаданные выгружаются исключительно успешным заданием и соответствуют одной
конфигурации; отсутствие хотя бы одной из шести успешных пар блокирует релиз.

## Тестирование и приёмка

- Обновить существующие тесты workflow/action, чтобы они разрешали и требовали
  только эту шестикомпонентную матрицу, `fail-fast: false`, по одному ZIP и
  одному мета-артефакту с уникальным slug на конфигурацию, неизменённый
  push-триггер и регрессионный контракт `upload_final_zip`: default `true` для
  существующих callers, условная внутренняя загрузка в composite action и
  явный `false` только для OP13 matrix workflow.
- Проверить регрессионный контракт `artifact_slug`: пустой default сохраняет
  прежнее debug-имя, непустое значение проходит basename-проверку, а OP13
  передаёт slug и использует его в имени debug ZIP и upload-artifact.
- Тестами проверить наличие конфигурации, корректный JSON и разрешение ссылки на
  манифест для всех шести элементов до начала сборки.
- Проверить список отслеживаемых XML через Git: количество равно шести и список
  в точности совпадает с таблицей.
- Запустить JSON-проверку и проверку разрешения манифестов, затем существующий
  workflow/action-тест.
- Тестами проверить нематричное publish-задание: зависимость от всех шести
  сборок, скачивание шести пар артефактов, проверку их числа, уникальных имён
  ZIP и SHA-256, единственный `gh release create`, точные тег и заголовок, а
  также отсутствие публикации при любой неуспешной сборке.
- Контракт publish должен отклонять `always()`, `failure()`, `cancelled()` и
  `continue-on-error`, проверять точные шесть download-артефактов, схему и
  отображение метаданных и передавать в `gh release create` только ZIP,
  прошедшие повторную SHA-256-проверку.
- Проверить, что описание релиза генерируется из метаданных в указанную таблицу,
  содержит только подтверждённые отображения совместимости и не выдаёт
  одинаковые конфигурации за разные регионы.
- Проверить `git status`: XML в `artifacts/**` не изменены и не удалены.

## Вне области работы

Не добавляются новые модели, регионы, конфигурации, способы запуска или
изменения прошивки. Не редактируются содержимое оставшихся манифестов, логика
ReSukiSU/SUSFS, закреплённые ревизии и нетрексируемые артефакты. Допускаются
только описанные необязательные входы composite action: `upload_final_zip` с
обратно-совместимым default `true` и `artifact_slug` с пустым default.

## Самопроверка проекта

Спецификация фиксирует единственный допустимый набор из шести конфигураций и
шести отслеживаемых манифестов, включает необходимые проверки до сборки,
изолированное поведение сбоев, атомарную публикацию одного общего релиза и
проверку сохранности `artifacts/**`. Регрессионный контракт загрузки сохраняет
поведение существующих callers и передаёт владение slugged ZIP и metadata
upload только OP13 matrix workflow.
